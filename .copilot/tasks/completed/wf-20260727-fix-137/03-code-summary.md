# Step 4: Code Summary — wf-20260727-fix-137

## Change

`.copilot/bootstrap-oidc.sh`:

1. New Step 1 (before the provider body is written): resolves Authentik's
   three built-in managed scope property-mappings — `scope-openid`,
   `scope-email`, `scope-profile` — by their stable `managed` identifier
   (not by PK, which is instance-specific) via
   `GET /api/v3/propertymappings/provider/scope/?page_size=100`, filtered
   in-process with `jq`. Fails loudly (`exit 5`) if any of the three
   isn't found, rather than silently proceeding without them.
2. The provider-creation body now includes the resolved PKs under
   `property_mappings`.
3. The reuse path (existing provider found) now also `PATCH`es
   `property_mappings` onto the existing provider and verifies the count
   is `>= 3`, self-healing any environment whose provider was created
   before this fix. Fails loudly (`exit 6`) if the patch doesn't stick.
4. Renumbered the remaining step comments (2 → 4, 5, 6, 7) to stay
   sequential.

No other files changed by the fix itself. `.copilot/oidc-provider-body.json`
was regenerated by actually running the fixed script against the local
Authentik instance (see `07-test-results.md`) — it's a tracked byproduct
artifact, not hand-edited.

## Why this shape (not the alternatives considered)

- **Hardcoding the three PKs directly in the JSON body** was rejected:
  property-mapping PKs are instance-specific UUIDs (confirmed by
  inspecting two different states of the local instance) — hardcoding
  would only work for the exact Authentik install it was captured from,
  silently breaking on any other instance (a fresh QA rebuild, a new
  contributor's local stack, etc.).
- **Filtering by `.results[].name`** (human-readable label) was rejected
  in favor of `.managed` (a stable identifier Authentik itself assigns to
  its built-in objects, unaffected by i18n/renaming) — `managed` is the
  correct, documented way to find a specific built-in object
  programmatically.
- **PATCH-on-reuse (self-heal) was added**, not just fix-on-create: the
  bug reporter's environment almost certainly already has a broken
  provider (the callback 401s today); a create-only fix would require a
  manual one-time DB intervention to also fix already-provisioned
  environments, which is worse operationally than an idempotent PATCH
  the script already does unconditionally for other reasons (mirrors the
  existing "refresh the provider body" idempotent-write pattern already
  in the script for `authorization_flow`/`invalidation_flow`).
