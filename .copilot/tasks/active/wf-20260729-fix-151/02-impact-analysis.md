# Step 2 — Impact Analysis: ISS-WEB-NEXT-SSR-JSDOM-001

## Issue

Every `/workspace/*` SSR route on `apps/web-next` 500s (local dev and
QA) because `jsdom@28.1.0` (declares `undici: ^7.21.0`) resolves against
`undici@8.8.0` instead, due to the root `package.json`'s open-ended
`pnpm.overrides.undici: ">=7.28.0"` letting resolution float past the
7.x/8.x major boundary. Full root cause in `01-issue-lookup.md`.

## Critical finding that changes the fix approach

A **blanket** version narrowing (`undici: ">=7.28.0 <8.0.0"` or similar)
is **not safe** — `testcontainers@12.0.4` (used by `apps/api`'s
Testcontainers-backed integration test suite, dozens of `*.spec.ts`
files) declares `undici: ^8.5.0`. A single global override cannot
satisfy both `jsdom`'s `^7.21.0` and `testcontainers`'s `^8.5.0`
simultaneously — one blanket pin always breaks the other consumer.

**Resolution:** use pnpm's **selector-scoped override syntax**
(`"<parent>>undici": "<range>"`, supported since pnpm 8.x — confirmed
pnpm 9.15.0 here via `packageManager` field) to pin `undici` differently
per dependent:

```json
"overrides": {
  "jsdom>undici": "7.29.0",
  "undici": ">=7.28.0"
}
```

This keeps the existing blanket `>=7.28.0` (preserving the original
CVE-fix intent for every OTHER undici consumer, including
`testcontainers`, which will still resolve to a current 8.x satisfying
both `^8.5.0` and `>=7.28.0`), while forcing `jsdom`'s specific resolved
copy to `7.29.0` — the latest 7.x, which itself satisfies `>=7.28.0` so
the CVE fix is not weakened for jsdom's copy either.

## Affected Layers

- **Root `package.json`** — `pnpm.overrides` gains one new
  selector-scoped entry. No other file needs a source change; this is a
  dependency-resolution fix, not an application-code fix.
- **`pnpm-lock.yaml`** — regenerated by `pnpm install` after the
  override change; will show `jsdom`'s `undici` entry drop from `8.8.0`
  to `7.29.0` while every other consumer (`testcontainers`, whatever
  else) is unaffected.
- **No apps/api or apps/web-next source code changes.**

## Risk Flags

### Security Review Required: yes (dependency/supply-chain angle)

- Confirm `undici@7.29.0` does not reintroduce the CVE(s) the original
  `>=7.28.0` override was meant to fix (verified in Step 1: `7.29.0 >
  7.28.0`, later patch release within the same major, so it can only
  carry the fix forward).
- Confirm the scoped override doesn't accidentally leave OTHER jsdom
  consumers (if any exist beyond `isomorphic-dompurify`) on the broken
  8.x — grep for all `jsdom` dependents before Step 4.
- Run `pnpm audit` after the change to confirm no new CVE surface opens
  from pinning `jsdom`'s undici to a specific 7.x patch instead of an
  open floor.

### Architecture Rule Risks: none identified

Dependency-version fix only, no architectural change.

## Test Scope

- **Unit/Integration:** run the full `apps/api` test suite (validates
  `testcontainers`'s `undici@8.x` path still works — this is the
  regression risk highest on the checklist, since `apps/api`'s
  integration tests are Testcontainers-heavy).
- **Live verification (the actual regression test for THIS bug):** curl
  every route the issue file documented as broken
  (`/workspace/admin/users`, `/workspace/admin/audit`,
  `/workspace/dashboard`) both locally, confirming 200 instead of 500.
  This is a live-environment regression test, not a unit test — the bug
  itself is only observable at the SSR-render boundary, not in any
  function's unit behavior.
- No new unit test is meaningful for "does jsdom's undici resolve
  correctly" — that's a package-manager-level fact, not application
  logic. The regression proof is the live 500→200 flip.
