## Requirement

**FEAT-AUTH-6** — Temporary account upgrade (Telegram-only → full member). This
migration adds the single new table the mechanism needs: `upgrade_intents`, a
short-lived, single-use token store that distinguishes an upgrade-completing
magic-link click from an ordinary sign-in at `AuthController.callback()`.

## Schema Changes

Module path: `apps/api/src/modules/auth/upgrade-intent.schema.ts` (new file).

New Drizzle table `upgradeIntents` (`upgrade_intents`), sibling in style to
`refreshTokens` (`apps/api/src/modules/auth/refresh-token.schema.ts`):

| Column | Type | Constraints |
|---|---|---|
| `id` | `uuid` | PK, `defaultRandom()` |
| `token_hash` | `varchar(64)` | NOT NULL, UNIQUE — SHA-256 hex of the raw token |
| `authentik_user_pk` | `integer` | NOT NULL — Authentik's plain-int `pk`, no FK (Authentik users are outside this Postgres database; cross-schema FK is architecturally impossible per ARCHITECTURE.md) |
| `telegram_id` | `varchar(32)` | NOT NULL |
| `target_email` | `varchar(255)` | NOT NULL |
| `created_at` | `timestamptz` | NOT NULL, `defaultNow()` |
| `expires_at` | `timestamptz` | NOT NULL |
| `consumed_at` | `timestamptz` | nullable |

Indexes:
- `upgrade_intents_token_idx` on `token_hash` — fast point-lookup at callback time.
- `upgrade_intents_authentik_user_pk_idx` on `authentik_user_pk` — idempotency check ("does this temp user already have a pending upgrade?").

Also matches `refreshTokens`' unique constraint idiom: `token_hash` carries
both a `.unique()` constraint (enforced at the DB layer, matching
`refreshTokens.tokenHash`) and its own non-unique btree index for the
lookup path — same shape drizzle-kit generates for `refreshTokens.tokenHash`
today, confirmed no divergence.

Barrel re-export added: `apps/api/src/db/schema/index.ts` now includes
`export * from '../../modules/auth/upgrade-intent.schema';`, inserted
directly after the existing `refresh-token.schema` line to keep the auth
module's schema files grouped together.

Deliberate divergence from the `refreshTokens` template (documented in the
schema file's header comment, called out in impact analysis's Architecture
Rule Risks section): `authentik_user_pk` is a plain `integer`, not a `uuid`
with `.references()`. A temp user has no `platform.users` row to reference
(that's this FR's entire premise), so there is no FK target and none was
added.

## Tenant Scoping

**Not tenant-scoped — confirmed correct, no `country_code` column added.**

Reasoning (from impact analysis, independently re-verified against
`standards.md` §VI before writing the schema): §VI's rule is "index tenant
columns (`country_code`) **on tenant-scoped tables**" — it is conditional on
a table being tenant-scoped, not a blanket requirement that every table
carry the column. `upgrade_intents` is not tenant-scoped because:

1. A Telegram user's country isn't resolved until well after upgrade
   (country/tenant assignment happens in a separate step referenced in
   `telegram-auth.service.ts`'s doc comments), and definitely not at
   `/upgrade-temp` request time, which only has `telegramId` + `email`.
2. `platform.users` itself — the table this FR's upgrade eventually
   populates — has no `country_code` column either. This matches
   ARCHITECTURE.md's "some data is global (users, badges, languages,
   tags)" bucket.
3. Direct sibling/template `refresh_tokens` is in the same global,
   non-tenant-scoped bucket and also has no `country_code` column.

No disagreement with the impact analysis's conclusion after independently
reading standards.md §VI in full — flagging per task instructions was
conditional on disagreement, which did not arise.

## Rollback Strategy

Standard reversible rollback: `DROP TABLE "upgrade_intents";` (also drops
its two indexes and unique constraint implicitly). Safe at any point after
this migration is applied, up until the FR's application code
(`/upgrade-temp` endpoint, `callback()`'s upgrade branch) is deployed and
in active use — once real upgrade intents exist and members are mid-flow
through a magic-link click, a rollback would strand any in-flight upgrade
(the member's `upgrade_intents` row disappears, their pending magic-link
click would 404/error at `callback()`'s lookup). No backup-restore need:
this is a net-new, empty-at-creation table, so a straight `DROP TABLE`
loses nothing that existed before this migration.
